# Easy Europe — Weekly Meeting App

Phase 1 of the build spec: the Monday management meeting on an EOS Level 10 structure,
replacing the free-text "Weekly Ladder" sheet.

## Run it now

```bash
npm install && npm run seed && npm run dev
```

No accounts, no database to provision. With no Supabase credentials the app uses a
file-backed store at `.data/db.json` and a "sign in as" picker in place of magic links.
An amber banner across the top says so, so nobody mistakes it for the real thing.

```bash
npm test        # 52 tests: the R1–R12 rule engine plus a three-week cycle on the real store
npm run build   # production build
```

## Going live on Supabase + Vercel

1. Create a Supabase project.
2. In the SQL editor run `supabase/migration.sql`, then `supabase/02-seed.sql`.
3. Authentication → Providers → Email: enable it, disable "Confirm email" if you want
   one-click magic links.
4. Set the three variables from `.env.example` in Vercel, and `NEXT_PUBLIC_SITE_URL` to
   your deployment URL. Add `<site>/auth/callback` to Supabase's redirect allow-list.
5. Deploy. The app switches to Supabase automatically once the URL and key are present.

**Before the first magic link goes out**, fix the email addresses in Admin → People. Only
`joshua@easyeurope.com.my` is confirmed; the rest are `firstname@easyeurope.com.my`
placeholders and sign-in will not reach anyone until they are corrected. Sign-in is
restricted to addresses already on the team list — there is no public access and no
self-registration.

`supabase/02-seed.sql` is generated by `npm run seed` from `src/lib/db/seed-data.ts`, so
the users and the eleven metric definitions have one source of truth. It is idempotent:
IDs are fixed, so re-running updates rather than duplicating.

## Where the rules live

Every non-negotiable from §5 is a named, tested function in
[`src/lib/rules.ts`](src/lib/rules.ts) — one place to ask "is this red?", so the UI never
decides for itself.

| Rule | Where |
|---|---|
| R1 blank renders red | `evaluateMetric` — a null value returns `off`, never a neutral gap |
| R2 no target renders grey | `evaluateMetric` returns `grey`, excluded from red counts; `metricsMissingTargets` feeds the Admin "decisions still open" panel |
| R3 exactly one owner | `assertSingleOwner` on every server action; owner fields are single-selects |
| R4 a to-do is 7 days | `defaultDueDate` (next Monday) + `isBeyondTodoHorizon`; the composer prompts past 14 days and offers to make it a monthly priority |
| R5 no solve without a to-do | `canSolveIssue`, enforced in `solveIssue` as well as the UI. The only hard gate, and it explains itself rather than silently disabling |
| R6 overdue to-dos carry themselves | `computeCarryForward`, run on every load of the runner. Idempotent via `todos.last_carried_meeting_id` |
| R7 completion % is computed | `reviewList` + `completionFor`. Scorecard line 11 is read-only and recomputes live as boxes are ticked |
| R8 issues sort by weeks open | `sortIssues` — the only sort offered |
| R9 max 3 issues | `canSelectMoreIssues` in the UI, re-checked in `toggleIssuePick` |
| R10 off-track → issue in one click | `issueTextForMetric` / `issueTextForPriority` pre-fill; `→ Issue` on every red row |
| R11 brain dump splitting | `splitBrainDump` — each non-empty line becomes its own issue, bullets and numbering stripped |
| R12 nothing retyped | Open to-dos, issues and priorities carry forward by query, never by re-entry |

## What is and isn't here

**Phase 1**, per §8: scorecard lines 1, 2, 3 and 6 live in week 1, weekly and monthly
priorities, to-dos, issues, and the full seven-section runner. All eleven metric
definitions are seeded — `live_from_week` and the rollout date in Admin reveal lines 4, 5,
7–11 on schedule without another deploy.

Not built, by agreement: the completion-% trend chart (phase 2), the departure readiness
board and `Departure` / `ReadinessCheck` tables (phase 3), quarterly planning (phase 4).
The seed is the five managers only; contributors get added in Admin → People when phase 3
needs them.

Out of scope per §9 and untouched: Google Sheet integration, Notion sync, native mobile,
automated data pulls, booking-curve modelling.

## Two deliberate departures from the spec's data model

Both are documented in the code where they appear.

- **`todos.last_carried_meeting_id`.** §4 defines `weeks_carried` as auto-incremented but
  gives it no idempotency key. Storing the meeting that last incremented it is what makes
  R6's "running twice on the same meeting date must not double-count" true by
  construction rather than by convention.
- **`issue_picks`.** The three issues picked for IDS need to survive a refresh mid-meeting
  and R9's cap needs to hold across five browsers, so the pick is a row rather than
  client state.

## Decisions the app is waiting on

These surface in Admin → *Decisions still open* rather than sitting in a document:

- **X, the tour window** (§10.1). Line 6 reads "within X (not yet agreed) weeks" until set.
- **Target for line 2**, 2027 signups per week (§10.2). Renders grey, not red, meanwhile.

## Architecture notes

- Next.js 15 App Router, TypeScript, Tailwind 4. Base font is 17px and nothing important
  is small grey text, so it holds up projected at 1.5× zoom.
- Every mutation is a server action in [`src/app/actions.ts`](src/app/actions.ts).
  Inputs autosave on a debounce; there are no save buttons in the runner. Meeting state
  lives in the database, so a refresh mid-meeting loses nothing.
- The data layer is one interface ([`src/lib/db/store.ts`](src/lib/db/store.ts)) with two
  implementations. Operations are granular rather than snapshot-and-overwrite: five
  managers submitting at once on a Monday morning would lose whichever write landed
  second.
- Row-level security in `supabase/migration.sql` is the real permission boundary. Everyone
  reads everything — the meeting is a shared screen and the readiness panel is meant to be
  public to the team — while writes are restricted to the row's owner, with the
  facilitator able to write anything because they drive the runner live.
- The local adapter reads from disk on every call. It cached the database in memory at
  first, which broke silently: Next loads server actions and page renders into separate
  module instances, so a cached snapshot goes stale the moment the other instance writes.
